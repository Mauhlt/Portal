# Portal sync: signed package delivery from the desktop to devices

**Owner decision (2026-11-12):** test builds and updates (e.g. the speech
model's NPU backend for the Snapdragon laptop) reach devices through Portal
sync, with directories laid out so nothing clashes.

This channel delivers code to the laptop, so it is security-critical.
Treat every rule below as a hard requirement.

**Status: implemented** (branch feat/sync). Everything below is in place
unless marked *deferred*; the concrete formats and flows are in
[Implementation](#implementation) at the end.

## Trust

* **A dedicated release-signing key** (Ed25519) lives on the desktop. It is
  separate from the TLS CA key and DPAPI-protected like it.
* **Pinned at pairing.** The device learns the release public key once,
  through the already-authenticated paired TLS channel, and pins it per
  server.
* **Signed manifest.** Every package version has one, covering: package id,
  version, a list of files {relative path, size, SHA-256}, the kind
  (`data` | `executable`), the minimum client version and the creation
  time. Devices verify the signature, then every file's hash and size,
  before anything is installed.
* **Unsigned or mismatched → rejected and logged.** A compromised web layer
  or network can't push code without the release key.
* **Approval on the device:**
  * `data` packages (model weights, trained adapter) install automatically;
  * `executable` packages require approval in the device's Portal app
    (package, version, publisher-key fingerprint, size), every new version.
  * Nothing is ever executed automatically, and nothing ever runs from
    staging.

## What is (and isn't) shipped

**Owner decision (2026-11-12):** vendor runtime DLLs, such as Qualcomm's
QNN/HTP libraries for the Snapdragon NPU, are **never** shipped through Portal.
They are already installed on the device, and packages load them from
there. NPU access is the owner's own Zig bindings, generated by the
**TranslateNPU** repo (modelled on TranslateVulkan) and compiled into the
programs that use them.

Packages carry only:
* the owner's compiled programs (e.g. `npu-probe`, `stt-local`, `portal-client`);
* the owner's data (`stt-model`, `stt-adapter`).

The first package is `npu-probe`, which reports where the installed QNN
runtime lives, its version and HTP arch, and runs one trivial graph.

**Delivered at pairing (owner decision, 2026-11-12):** when a laptop is
paired, the desktop offers it the voice packages it is subscribed to:
`stt-local` (executable, approval required), `stt-model` and `stt-adapter`
(data). The laptop app shows "Install voice model?" right after pairing;
after that, new adapter versions arrive whenever training produces one.

## Directory layout on the device

**One folder per paired desktop (owner decision, 2026-11-12):** "paired
desktops on the laptop go to their own folder to prevent
overlapping/overwriting".

```
%LOCALAPPDATA%\Portal\sync\desktops\<host>-<key>\
                                   one per paired desktop: <host> is the
                                   pinned IP_PORT (10.8.0.1_8420), <key> the
                                   first 16 hex digits of the SHA-256 of the
                                   release key pinned for it
  staging\<random>\                download + verify area (deleted after)
  packages\<package>\<version>\    verified, read-only, immutable
  state\<package>.txt              one record: signer, current, previous,
                                   highest sequence (temp + MoveFileEx)
  data\<package>\                  the package's own writable state
```
(macOS `~/Library/Application Support/Portal/sync/desktops/...`, Linux
`$XDG_DATA_HOME/portal/sync/desktops/...`.)

* **Desktops never share anything.** Every pointer, highest sequence,
  install and approval belongs to one desktop's folder; desktop B
  publishing `foo` at a huge sequence cannot replace desktop A's `foo` or
  block A's updates. The same address paired with another release key is
  a different folder (pairing again starts clean).
* Every record names the release key (SHA-256) that signed what it points
  at; a record naming another key is refused, never overwritten.
* **Earlier builds** used one shared store (`sync\packages`, `sync\current`,
  `sync\previous`, ...). It is never read or written any more (its
  pointers could have come from any desktop); `portal connect` notes it
  once, and it can be deleted by hand once nothing runs from it. Packages
  are fetched again into the desktop's own folder.

* **Package ids** are a fixed namespace: `portal-client`, `stt-local`,
  `stt-model`, `stt-adapter`, `npu-probe`, … (`[a-z0-9-]{1,32}`).
* **No shared folders.** A package can write only to `data\<package>\`, and
  nothing writes into `packages\`.
* **Versions** are validated (`[0-9A-Za-z.+-]{1,64}`, no `..`). Paths inside
  a manifest are relative, normalised, and must stay inside the version
  folder: no `..`, no drive letters, no ADS (`:`), no reserved device names.
* **Running programs are never overwritten.** A new version is a new
  folder. Pruning keeps current, previous and any version still in use.
* **Quotas:** per-package size caps and total sync cap (8 GiB per
  package version, 32 GiB per desktop's store by default).

## Desktop side

* `portalctl publish <package> <folder> [--kind data|executable]` hashes the
  files, signs the manifest and stores the version under
  `%LOCALAPPDATA%\Portal\publish\<package>\<version>\`.
* **Device subscription:** the owner chooses per device which packages it
  receives (e.g. `stt-npu-test` only to the laptop).
* **Event-driven delivery:** an `{"t":"updates", ...}` message on the
  interactive WebSocket announces new versions to subscribed devices.
  Devices fetch manifests and files on the bulk WebSocket (`/ws/bulk`, its
  own connection with the bulk priority, 16 KiB chunks), with explicit size
  limits. Nothing polls.

## Running delivered programs: `stt-local`

* `stt-local` runs as a **child process of the Portal app**, not linked in.
  This gives crash and hang isolation from the NPU driver, keeps the vendor
  DLLs out of the process holding device credentials, and allows
  independent updates.
* **Protocol:** JSON lines on stdin/stdout, treated by Portal as
  **untrusted input**:
  * the first line is a `ready` event with the protocol version;
  * stdout carries protocol lines only (≤ 8 MiB each); logs go to stderr;
  * requests carry `rid` and replies echo it; fixed error codes;
  * 16 kHz mono s16 PCM in, text out;
  * `wakeup` events keep it event-driven;
  * stdin EOF means exit.
* **Restrictions** stt-local must honour: no sockets, no spawning, writes
  only under its profile dir (`sync\data\stt-local\`). It runs from its
  read-only package folder, with the model and adapter from their own
  package folders.

## Diagnostics back to the desktop (proposed)

A device-to-desktop report upload for programs such as `npu-probe`: the
laptop app offers "Send report to desktop" (with approval) and
`POST /sync/report/<pkg>` stores it under the desktop's Portal data folder,
with size caps.

## The other direction

Device → desktop data (speech samples and corrections) uses the bundle
endpoints in `docs/stt-sync-contract.md`.

## Tests required

* Signature and hash verification, plus every rejection path: bad signature,
  wrong key, hash mismatch, path traversal, oversize, downgrade.
* Atomic install and rollback.
* Executable approval.
* Never overwriting a running exe.
* Privacy scan.


## Implementation

Code: `client/src/sync/` (shared format and the device side: `manifest.zig`,
`store.zig`, `keypin.zig`, `engine.zig`, `ui.zig`), `src/sync.zig` (desktop
stores), `src/sync_cli.zig` (portalctl commands), the `/sync` routes and
the `updates` message in `src/web.zig`, `SyncWatch` in `src/main.zig`.

### Manifest (canonical text)

```
portal-manifest-v1
package <id>                [a-z0-9-]{1,32}, no leading/trailing '-', not a device name
version <version>           [0-9A-Za-z.+-]{1,64}, no "..", no leading/trailing '.', not a device name
kind <data|executable>
sequence <n>                1..2^63-1, monotonic per package (downgrade/replay protection)
created <unix seconds>
min-client <d[.d[.d[.d]]]>  numeric, compared with the device's Portal version
files <count>               at most 4096
file <size> <sha256> <path> one per file, sorted by path (bytewise)
end
```

* ASCII only, LF line ends, single spaces, decimal numbers without leading
  zeros, lowercase hex. The path is the rest of its line.
* **One encoding only**: the parser rejects anything that does not
  re-encode to the identical bytes, so the signed bytes are the bytes
  interpreted.
* Caps: 4096 files, 260-byte paths, 32 levels, 8 GiB per version, 2 MiB per
  manifest.
* **Paths**: relative, '/'-separated, no empty / `.` / `..` component, no
  leading '/', no drive (`C:`), no backslash, no `:` (alternate data
  streams), printable ASCII without `<>"|?*`, no leading space, no trailing
  dot or space, no reserved device name (CON, PRN, AUX, NUL, COM0-9,
  LPT0-9, CONIN$, CONOUT$, CLOCK$, also with an extension such as
  `nul.txt`), and no two paths equal ignoring case (nor a file that is also
  a folder name).
* **Signature**: Ed25519 (std, `verifyStrict`) over the exact manifest
  bytes. The publisher key fingerprint is the SHA-256 of the 32-byte
  public key, shown as `AB:CD:...`.

### Trust and pinning

* `portalctl sync key [show | init [--force]]`. The key is a 32-byte
  Ed25519 seed in `%LOCALAPPDATA%\Portal\sync-key\release.key`
  (`PORTAL-SYNC-KEY-V1` + a DPAPI current-user blob with its own entropy
  purpose, "Portal sync release key v1", so it can't be swapped with the
  CA key's blob) and the public key in `release.pub`, which must match on
  every load. `portal run` creates it on first start, like the CA. It is
  decrypted only to sign a publish.
* **Pinned at pairing**: on its first connection after pairing (the CA
  pinned by the SHA-256 in its pairing code), a device asks `get key` on
  the bulk WebSocket and pins the key in `<per-user config>\servers\<host>.sync-key`
  (next to the CA pin; public data). A key change on the server is refused
  (the CLI warns); only pairing again replaces the pin. Devices paired
  before sync existed must be paired again.

### Desktop

* `portalctl publish <pkg> <folder> --kind data|executable [--version V]
  [--min-client V]` walks the folder (regular files only; links refused),
  refuses unsafe paths with the reason, copies each file into
  `publish\<pkg>\.tmp-<random>\files\<n>` while hashing it (what is stored
  is what is hashed), writes `manifest.txt` and `manifest.sig`, verifies the
  signature, and renames the folder to `publish\<pkg>\<version>`. The
  sequence is reserved first in `publish\<pkg>\history.txt`; sequences and
  version names are never reused, even after `unpublish`. The default
  version is the sequence number.
* `portalctl publish --list`, `portalctl unpublish <pkg> <version>`.
* Subscriptions: `%LOCALAPPDATA%\Portal\sync-subscriptions.txt` (locked
  read-modify-write, flushed temp file, MoveFileEx WRITE_THROUGH), via
  `portalctl sync subscribe|unsubscribe <device> <pkg>`, `portalctl sync
  subscriptions`, or the Devices panel (P on a device row).
* The server serves the stores as they are and does not need the key: it
  parses manifests strictly to build the index (a manifest that does not
  parse, e.g. one naming `../x`, is never listed or served) but the
  signature is the device's to check.

### Endpoints

See [protocol.md section 7](protocol.md#7-portal-sync-signed-packages-for-paired-devices):
`get key`, `get index`, `get manifest <pkg> <ver>` (signature in the reply
header), `get file <pkg> <ver> <n>` (by index, streamed in 16 KiB chunks,
each under the send deadline; a stored file whose size differs from the
manifest is not served), on the bulk WebSocket. Each serves only the
connection's own device (by its tunnel address) and its subscriptions
(404 otherwise).

**Announcements.** `SyncWatch` waits on two directory change notifications
(the data folder, for the subscriptions and device files, and `publish\`
with its subtree) and nothing else. On each wake it hashes every
subscribed device's index; each WebSocket writer sends `{"t":"updates"}`
when its device's hash changed.

### Device install flow

`client/src/sync/engine.zig`, the same code in `portal connect` (a worker
thread woken by every stream connect and `updates`) and `portalctl
sync-device` (headless, for tests):

1. `get index`; then per line, `get manifest`;
2. SHA-256 of the manifest = the index line; signature verifies with the
   pinned key (first: nothing unsigned is interpreted); strict parse;
   package, version, sequence, kind and size = the index line;
3. store policy: sequence above the highest ever installed for the
   package (else *downgrade* or *replay*, refused), client new enough,
   quota;
4. `data` continues; `executable` stops as *waiting for approval* unless
   that exact manifest (package, sequence, SHA-256) was approved;
5. each file `GET .../file/<n>` into `staging\<random>\<n>` (created
   exclusively), bounded by the manifest size and hashed as it arrives;
   any mismatch deletes the staging folder and nothing changes;
6. the files move into `packages\<pkg>\.incoming-<random>\<path>` (no
   replace), each marked read-only; the manifest and signature go to
   `packages\<pkg>\.manifests\<ver>.{txt,sig}`; the folder is renamed to
   `packages\<pkg>\<ver>` (an existing version folder is never written: the
   same version must come back with the identical manifest, else refused);
7. `state\<pkg>.txt` := one record (old current becomes previous, the new
   version current, the highest sequence installed, the signer), written
   as a flushed temp file + one MoveFileEx REPLACE_EXISTING |
   WRITE_THROUGH: a crash leaves the old record or the new one, never a
   half-moved pair;
8. `data\<pkg>\` is created; versions other than current and previous are
   pruned unless a file in them can't be opened exclusively (a running
   program), in which case they stay.

Leftover staging, `.incoming-*` and `.trash-*` folders are removed at the
start of every pass. Rollback (`sync-device --server S --rollback <pkg>`,
Roll back in Packages) swaps current and previous in one record write and
keeps the highest sequence, so the version rolled back from is not taken
again.

**Revoke** (`sync-device --server S --revoke <pkg>`, Revoke in Packages,
after a confirmation): withdraws an executable's approval. The previous
version becomes current, or, without one, the package is uninstalled; the
highest sequence is kept, so the revoked version is never installed again
(only a newer one, which asks for approval again). Its folder is pruned
unless something still runs from it. `data\<pkg>\` is kept.

**Forget this desktop** (Packages, after a confirmation; `portal connect
--server S --forget`; `sync-device --server S --forget`) is mutual. First
the device asks the desktop to remove it (`POST /device/forget` with its
session, or a fresh sign-in; docs/protocol.md section 1): the desktop
removes the record, ends its sessions and refreshes its Devices panel.
Then, whatever the answer, it deletes the device's credentials for it,
the pinned CA and release key, every `desktops\<host>-*` folder (renamed
to `desktops\.trash-*` first, then deleted; folders a running program
holds stay and are reported) and the remembered last server if it was
this one. If the desktop could not be reached, the report says it still
lists the device until it next sees it or the owner unpairs it there.
`portal connect` exits afterwards.

**Unpaired at the desk** (Devices panel, `portalctl unpair`; also a
device the desktop revoked or replaced): the desktop says so explicitly,
with `logout` reason `unpaired` to a connected device and
`X-Portal-Device: gone` on its next sign-in. The device then runs the
same local forget automatically and says why (portal connect shows it
and exits; sync-device prints it and exits 1). Only that explicit answer
does this: a refused or failed sign-in without it never deletes pins or
packages.

**The shared store of earlier builds** (`sync\packages`, `sync\current`,
`sync\previous` directly under the sync root, from before per-desktop
folders) is deleted when portal connect or sync-device starts: each entry
is renamed to `sync\.trash-*`, then deleted; anything still in use stays,
is reported, and is retried on a later start. `sync\desktops\` is never
touched.

**One writer.** In `portal connect` only the sync worker thread touches
the store. The UI posts Roll back / Revoke / Forget as an atomic pending
op (the package name written first, under the panel mutex) and sets the
worker's wake event; the worker performs it before its next pass or
between two packages of a pass (Forget only between passes). The UI never
mutates the store, so a rollback can't race an install or prune.

### UI

* `portal connect`: "Install <pkg> <ver> from <desktop>?" with the
  publisher key SHA-256 and size; "Install voice model?" after pairing
  when voice packages are subscribed (Install also approves stt-local; Not
  now holds them for this run); Packages (Ctrl+Shift+K): installed data
  with Roll back, installed programs with Revoke, versions waiting for
  approval with Approve, rejected ones with the reason, and Forget this
  desktop. Revoke and Forget ask for confirmation (Cancel focused).
* **No accidental approval (owner decision, 2026-11-12).** The approval
  panel can open by itself after a background pass, while the user is
  typing into the remote terminal, and takes the keyboard. So there are no
  letter shortcuts (the old `y`/`n` are gone; typed characters are
  swallowed while a panel is open); the focus starts on the safe button
  (Reject / Not now / Close / Cancel); and every key and click is ignored
  until the panel has been on screen for 600 ms, measured from the frame
  that really presented it (no timer: each input compares its own time).
  Only Approve activated as a button (a click, or Tab to it and Enter)
  approves. A later pass asking the same question keeps the panel, its
  focus and the guard already served.
* The desk: Devices shows each device's package count; P on a row opens
  its packages (known ids and everything published) with
  Subscribe / Unsubscribe.

### Tests

* Unit: manifest canonical form, every non-canonical variation, a fuzz
  loop (random, truncated and mutated input; anything accepted
  re-encodes identically); every path rule; signatures good / tampered /
  wrong key; index strictness; store: atomic install, read-only files,
  upgrade, downgrade and replay refused, rollback, hash and size
  mismatches in staging, quota, staging cleanup, an existing version
  folder never written, a held-open ("running") exe whose version folder
  is kept while new versions land in new folders; release key DPAPI
  round trip and purpose binding; publish, sequences, names never reused,
  per-device index; subscriptions file; the panels' state machines.
* e2e group `sync` (port offset 110, TLS on): see `tests/e2e/sync_tests.zig`.

### Deferred

* Running installed programs (e.g. launching `npu-probe` from Packages):
  nothing runs packages yet.
* Self-update of `portal-client` through sync, and publishing from the
  desk window (publishing is `portalctl publish` only).
* Quotas are fixed (8 GiB per version, 32 GiB per desktop); no setting yet.
* Approvals given in the app are kept in memory for the run (an
  approved manifest installs at once, so nothing more is needed); a
  revoke is recorded on disk through the highest sequence.
* The old shared store of earlier builds is not migrated: it is deleted
  (see Forget this desktop above).
* A device-side end-to-end test of a *signed* path-traversal manifest:
  the server never offers one, and device-side rejection is covered by
  unit tests.
